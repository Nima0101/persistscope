# OSS landscape

Public-source research, 2026-10-06. No claim of exhaustive coverage.

## Source evidence and candidate-specific scope

1. Crash-state explorer: [CrashMonkey](https://github.com/utsaslab/crashmonkey) records/replays filesystem workloads using kernel modules; [setup documentation](https://github.com/utsaslab/crashmonkey/blob/master/docs/CrashMonkey.md) recommends VMs. [LazyFS](https://github.com/dsrhaslab/lazyfs) provides a FUSE layer with data-loss and torn-write faults. [Pathfinder](https://github.com/efeslab/Pathfinder) is a recent reusable application crash-consistency research artifact, with native tracing and Linux-oriented dependencies. This proves the domain has serious incumbents, but gives a plausible portability/setup niche, not algorithmic novelty. [durable-replace](https://github.com/nradawg/durable-replace) already models power cuts for atomic replacement, so multi-file model composition and reusable assertions must be central. [SQLite testing](https://www.sqlite.org/testing.html) documents the value of fault and crash testing.

2. Durable edge execution: implement authorized side-effect intents, durable decisions, leases, and explicit unknown outcomes. It offers high real utility but a larger security/operational burden; portable safe filesystem adapters and signing/replay boundaries are difficult to polish together. [durable-agent-outbox](https://github.com/mstevens843/durable-agent-outbox) is a direct overlap, documenting unknown outcomes, signed receipt authentication, and reconciliation. Research therefore weakens the claim that an edge-outcome ledger alone would be distinct.

3. Local linearizability checker: consume JSONL histories, provide register/map/queue specifications, bounded checking, and minimized counterexamples. [Porcupine](https://github.com/anishathalye/porcupine) already combines optimized checking with visualizations and custom executable models, while [porcupine-rs](https://github.com/erwin-kok/porcupine-rs) covers another systems language. [S2 verification](https://github.com/s2-streamstore/s2-verification) demonstrates real use in a concrete storage service. A new generic checker needs meaningful reduction or integration advantages to justify itself.

4. Artifact reproducibility auditor: independently rebuild selected native releases with controlled environment perturbations, identify nondeterministic sections, and emit evidence bundles. [diffoscope](https://diffoscope.org/) already specializes in detailed recursive artifact comparison. [reprotest](https://github.com/SantiagoTorres/reprotest) automates environment variation. A lightweight portable release-focused workflow could help, but broad binary-format support risks becoming shallow glue and arbitrary builds introduce execution boundaries.

5. Schema compatibility witness generator: compare a carefully bounded JSON Schema subset and produce a concrete old-valid/new-invalid payload instead of only structural diffs. [oasdiff breaking-change docs](https://github.com/oasdiff/oasdiff/blob/main/docs/BREAKING-CHANGES.md) and [OpenAPI 3.1 issue](https://github.com/oasdiff/oasdiff/issues/793) show semantic complexity and established competition. [Buf](https://buf.build/docs/breaking/) already offers layered Protobuf compatibility checking. Witness generation is potentially valuable but complete JSON Schema implication is too large for this mission; partial coverage must be explicit.

6. Deterministic network-fault scenario runner: replay byte-budget failures, resets, delays, and half-close schedules with trace evidence. [Toxiproxy](https://github.com/Shopify/toxiproxy) already serves test/CI network faults and supports deterministic manipulation. Potential distinction is protocol-independent replay/minimization and strict schedules, but a new proxy risks adding another controller around a solved transport problem.

7. SQL migration concurrency-risk simulator: model or exercise concurrent readers/writers during candidate PostgreSQL migration sequences and explain blocking witnesses. [Squawk](https://github.com/sbdchd/squawk) already lints unsafe migrations. An executable lock witness adds depth beyond linting, but broad claims require real PostgreSQL versions and workloads, making a polished cross-platform five-minute experience harder.

8. Resumable transfer integrity verifier: adversarially exercise upload implementations across restart, offset conflicts, corruption and incomplete completion; emit protocol transcripts. [tus protocol](https://github.com/tus/tus-resumable-upload-protocol) and [tusd](https://github.com/tus/tusd/blob/main/README.md) provide mature protocol and implementation targets. The [negative-length advisory](https://github.com/filebrowser/filebrowser/security/advisories/GHSA-ffx7-75gc-jg7c) gives concrete input-validation motivation. A conformance verifier is more distinct than another transfer server, but security and interoperable target harnesses expand scope.
